## F01 — explicit Product contract delta (not semantics-preserving)

The legacy Passlib implementation accepted passwords longer than bcrypt's 72-byte input limit during new account creation and silently truncated. The candidate **deliberately rejects** a newly supplied password longer than **72 UTF-8 bytes** or containing NUL, with **HTTP 422** at POST /api/v1/users/register before lookup, hash or CRUD. Exactly 72 bytes are permitted, including multi-byte Unicode; 73+ bytes are not. UserCreate and internal UserUpdate validate the same way. Empty password remains allowed under the current schema; minimum password strength is separate future policy.

The public contract and existing-user recovery boundaries are documented in [auth-password-policy-candidate.md](../contracts/auth-password-policy-candidate.md). The React registration screen now states the byte limit and the API client maps a password-field 422 validation array to an actionable message without exposing raw objects or logging passwords. A valid registration remains 201, duplicate email 400. This is a **material API validation change** subject to later Developer acceptance, not an unchanged auth contract.

Existing $2a$/$2b$/$2y$ hashes, including passwords originally longer than 72 bytes, remain verifiable; no database read/write of real accounts, forced reset, bulk rehash, schema change or JWT change. Existing users can keep logging in; voluntary recovery/password change must follow the new policy when a separately authorized update flow exists. **No public password-update endpoint currently exists**; do not invent one.

## A04 — inherited bcrypt verification alias

New bcrypt 4.3.0 creation never silently truncates. However, bcrypt verification inherently compares only the first 72 bytes. A newly created hash of exactly 72 bytes also verifies a candidate string with a suffix appended, including multi-byte Unicode boundary cases. Added explicit new-hash regression tests and negative tests where a multibyte character crosses byte 72. This is a **known inherited authentication ambiguity**, not a claim of full-string verification or a newly introduced creation policy. Altering verification semantics would require a separate Product migration decision.
